# Dizko MCP Deep Audit

Date: 2026-09-08. Package `dizko-events` 0.7.6 at commit `6ee987b`.

## Scope and method

The audit covered the full MCP surface: all 24 tools, both transports, the HTTP host, the ranking and personalization layer, the ticket flow, the calendar output, tests, and documentation. Every claim below was reproduced, not inferred from reading code.

How it was run:

- The hosted endpoint `mcp.dizko.app` was unreachable from the audit sandbox, so the server was started locally from this commit and pointed at the live `api.dizko.app`. Everything a hosted client sees was exercised except two hosted-only behaviors: the `X-Dizko-MCP-Secret` header (the DJ directory endpoint returns 403 without it, so mixes and press clips were verified only through the entity profile path that succeeded) and the Railway proxy's `X-Forwarded-For` handling.
- 120 tool calls were made against live inventory with realistic DJ, venue, city, and date inputs, plus the complete preference lifecycle and the complete ticket flow, including a tampered quote token.
- The upstream `/events`, `/cities`, `/scene/*`, and `/promoters/*` endpoints were probed directly to see what data the MCP drops or misrepresents.
- Three parallel deep dives were run on documentation drift, test coverage, and MCP SDK 2.0 conformance. Their findings are integrated below and reproduced in the appendices.
- `npm test` passes: 151 tests, 96% line coverage, 81% branch coverage.

## What is genuinely good

- Response cache with stale-serve and in-flight deduplication. A cold Berlin weekend search took 1033 ms and the repeat took 15 ms. Twenty identical parallel requests completed in 369 ms total. Twenty distinct cities in parallel completed in 1.5 s.
- Retry with backoff and jitter, and consistent scrubbing of internal hostnames and upstream bodies from every error the model sees.
- Consent-first profiles, hashed secrets, timing-safe comparison, and a retention prune that runs on every read.
- The 2026-07-28 revision and 2025-era clients are served from one server definition with correct cache hints; the SDK audit found no protocol violations.
- Explainable ranking reasons on every recommended event.
- Short redirect links for calendar and directions keep per-event payloads down.
- Artist search quality is high. "who is peggy gou" as a raw query still returned Peggy Gou first, and every well-known DJ tested resolved to the correct profile.

## Priority 0: wrong answers reaching users

### F1. Event times are wrong for every city outside UTC

Every `starts_at` is emitted as UTC and the render template tells the model to print "weekday, date, start time" from it. Nothing in the payload or the instructions says these are UTC.

Evidence:

- Berlin event `3d0ba4fd` is served as `2026-09-09T17:00:00+00:00`. Local start is 19:00.
- The New York `plan_night` primary is served as `2026-09-12T02:00:00+00:00`. Local start is Friday 22:00, and the model will present it as Saturday.
- Upstream filters by the city's local date. A Los Angeles single-day query for 2026-09-11 returned 100 events whose UTC date is 2026-09-12. The MCP then hands those UTC strings to the model as if they were local.

The same bug exists on the input side. `resolveDateRange` in `src/dateRange.js:34-36` builds "today" from the server process clock. On a UTC host, a Los Angeles user asking for "tonight" at 18:00 on Friday gets Saturday's events. Reproduced: at `2026-09-12T01:00:00Z`, "tonight" resolves to 2026-09-12 under `TZ=UTC` and to 2026-09-11 under `TZ=America/Los_Angeles`. The test suite itself fails 8 tests under `TZ=Pacific/Kiritimati` because fixtures assume noon UTC is the same calendar day everywhere.

Fix:

- Add a static city-to-IANA-timezone map for the 47 known cities in `src/config.js`. Upstream has no timezone field, but every event carries `venue_city`, so this is enough.
- In `summarizeEvent`, emit `starts_at_local` (RFC 3339 with offset), `timezone`, and a preformatted `when` string such as "Fri 11 Sep, 19:00". Keep `starts_at` in UTC for machines. Instruct the model to render `when` verbatim.
- Resolve `when` presets in the target city's timezone, not the server's. `resolveDateRange(preset, now, timezone)` is a small change; the city is known for every search that has one.
- Pin `TZ=UTC` in the `test` script and add a near-midnight case in two timezones.

### F2. Personalization collapses recall by turning saved taste into hard filters

`personalizedSearchInput` in `src/tools.js:983-1000` copies saved `genres`, `vibe`, `event_types`, `neighborhoods`, `max_price` and `free` into the upstream query. Upstream applies them as AND filters. The July QA report fixed this for venues only.

Evidence from a profile saved with genres techno/house, vibe underground, max_price 30:

| Request | Unpersonalized count | Personalized count |
| --- | --- | --- |
| Berlin, weekend | 523 | 7 |
| Berlin, Sunday 2026-09-13 with `day_filters.sunday.max_price = 15` | 207 | 0 |

The Sunday case shows `max_price` from a per-day filter becoming a hard `price_max` upstream filter, and 27 of 50 Berlin events have no price at all, so a price filter also removes every unpriced event. The user is told there is nothing on.

Fix: only fields the user typed in the current request become upstream filters. Saved and learned taste goes into `preferences` for `rankEvents` only, which already gives +18 per genre match and -30 for over budget. Raise the candidate `limit` to 100 for personalized calls so the ranker has something to rank. Keep `cities[0]` as the city fallback. Add a regression test asserting that a profile with three saved genres does not add `genres=` to the upstream URL.

### F3. One negative feedback poisons the profile

`updateLearnedSignals` in `src/preferences.js:298-319` applies weight -1 to every genre, vibe, event type and venue of a disliked event. `learnedToPreferences` then puts any negative term into `avoid`, and `rankEvents` charges -25 per avoid term.

Reproduced with a profile whose saved genres are techno and house:

- One `liked: false` on a crowded techno party produced `avoid: ["techno", "free-entry", "queer-friendly", "party", "amt"]`.
- The same Klubnacht-style event scored +52.4 before that feedback and -47.6 after it. The user's number one saved genre is now a penalty.
- The note "the commercial break was long" produced `avoid: ["mainstream"]`. The note "not bad music at all" registered as a negative music signal.

Fix:

- A dislike without notes should target what is specific to that event: the venue and the promoter, not the genre or event type. Apply genre and type penalties only when the notes mention music or lineup.
- Never let a learned avoid term override a saved preference. If a term is in `preferences.genres`, cap its learned score at 0.
- Require a cumulative score of -2 or lower before a term enters `avoid`, so one bad night is a data point rather than a rule.
- Tighten the note regexes: exclude "not bad", "not too", "not the worst", and require the negation to be within a few words of the noun.
- Surface `learned_preferences` in the `personalization` block with the score, and give the model an instruction to tell the user when a learned avoid is shaping results so the user can correct it.

### F4. Flagship venue profiles show zero upcoming events

`getEntityProfile` in `src/entities.js:143-159` searches upstream with `venue=<profile name>` and then keeps only events whose `venue_name` exactly equals the profile name after lowercasing.

Evidence, measured against live data:

| Venue | Profile name | Upstream `venue=` matches | Events the MCP returns |
| --- | --- | --- | --- |
| Berghain | Berghain / Panorama Bar | 0 (event venue is "Berghain \| Panorama Bar \| Säule") | 0 |
| Tresor | Tresor | 43 (event venue is "Tresor / Globus") | 0 |
| RSO | RSO Berlin | 0 (event venue is "RSO.Berlin" or "RSO.BERLIN") | 0 |
| Sisyphos, Watergate, Renate | various | 0 | 0 |
| Basement | BASEMENT | 13 | 6 |
| Nowadays | Nowadays | 45 | 35 |

A user asking "what's on at Berghain this weekend" through the venue profile gets an empty list while `search_events` with `venue: "Berghain"` returns 39 events.

Fix: match on normalized tokens rather than equality. Split both names on `/`, `|`, `.`, `-` and whitespace, drop stop words like "berlin" and "club", and accept an event when the profile's first token set is a subset of the event's. Send the first token to upstream `venue=` instead of the full profile name. Longer term, ask the API team for a venue id on events so this stops being string matching.

### F5. The model cannot see what parameters mean

`compactInputSchema` in `src/tools.js:471-477` deletes every `description` and `default` from every input schema before serving. `publicToolDefinition` drops every `outputSchema`. This was done in the registry-prep commit to stay under a self-imposed 20,500-byte tool list budget, and it was also when every tool description was cut to a single sentence.

What the model receives for `search_events` today:

```json
{"city":{"type":"string"},"when":{"type":"string"},"query":{"type":"string"},"limit":{"type":"number"}, ...}
```

Consequences observed in this audit:

- `when` accepts only eight presets, but the model is never told which. `when: "friday"` and `when: "next weekend"` are natural guesses and both fail (see F6).
- `limit` above 200 fails upstream; the model is not told the cap. `limit: 500` returned "The request was not valid".
- `max_price` and `price_max` both exist on five tools with different semantics (ranking hint versus hard filter). `limit` and `result_limit` both exist on four tools. With no descriptions, they look interchangeable.
- `kind` on `find_scene_entities` is required and offers `dj` and `artist` as separate choices that mean the same thing.
- The SDK never validates input against these schemas (see Appendix C), so `$ref`, `anyOf`, `dependentRequired`, `enum`, `minimum` and `maximum` are advisory to the model and enforced by nobody. `city: 123` reached the tool and was stringified. `rating: 7` is accepted. `quantity: "2"` is accepted.

Fix:

- Stop stripping descriptions and defaults. Measured cost: the full list would be roughly 27 KB instead of 20 KB. That is well inside what Claude and ChatGPT accept, and the budget test in `test/mcpServer.test.js:116` is the only thing enforcing it. If a budget matters, keep descriptions on the parameters where the model has to guess (`when`, `query`, `kind`, `limit`, `sort_by`, `max_price`) and drop the rest.
- Rewrite tool descriptions to carry the routing rule, the key inputs, and what comes back. Server `instructions` are not surfaced by every client, so the description is the only text guaranteed to reach the model. A good shape: "Search live Dizko events in one city. Use for any 'what's on' request that names a city. `when` accepts today, tonight, tomorrow, weekend, week, or YYYY-MM-DD; `query` is semantic. Returns up to `limit` events with local times and links; `count` is the total available."
- Validate inputs server-side with the schemas you already wrote. `@modelcontextprotocol/server` 2.0 ships Ajv; a ten-line validator in `callTool` turns type errors into `invalid_argument` results with the field name.
- Delete the duplicates: keep `price_max` (filter) and `result_limit` (how many to return) and alias the others silently.

### F6. Bad input produces a generic error the model cannot act on

`callTool` catches everything and routes non-HTTP errors to "The request could not be completed." with code `request_failed`.

| Input | What the model gets |
| --- | --- |
| `when: "friday"` or `"next weekend"` | request_failed |
| `quantity: 13` or `0` on a quote | request_failed |
| A malformed `quote_token` | request_failed |
| `limit: 500` | invalid_request, no field named |
| `get_event` with a non-UUID id | invalid_request instead of event_not_found |
| `get_daily_roundup` with `date: "12/09/2026"` | silently returns today's digest |
| `get_daily_roundup` with `when: "weekend"` | silently returns Friday |
| `city: "Berlin, Germany"` | unsupported_city, no nearest city |
| Profile errors | no `code` field at all |

Fix: introduce one error shape `{ error, code, field?, allowed?, hint? }` and use it everywhere. Validate `when`, `limit`, `quantity`, `date`, and `quote_token` before any network call. Strip a trailing country from `city` and try again before declaring it unsupported. Map upstream 422 validation details (they name the field and the constraint) into `invalid_argument`. Make silent fallbacks loud: if a date cannot be parsed, say so.

## Priority 1: quality, cost, and safety

### F7. Payloads carry 40% dead weight and are sent twice

Every result is serialized into both `content[0].text` and `structuredContent`, so the wire carries each byte twice. Some clients feed both to the model.

Measured on live data:

| Call | Text tokens (approx) | Wire size |
| --- | --- | --- |
| `search_events` Berlin weekend, 12 events | 4,200 | 33 KB |
| `search_events` limit 50 | 15,100 | 118 KB |
| `get_daily_roundup` Berlin | 9,600 | 75 KB |
| `get_artist_events`, 5 artists | 6,000 | 47 KB |
| `find_scene_entities` DJ profile | 3,800 | 30 KB |

Where the bytes go in a 50-event search, by field: `description` 17%, `lineup` 10%, `promoters` 10%, `directions_url` 7%, `calendar_url` 7%, `image_url` 7%, `event_url` 7%.

Specific waste:

- `description` is upstream boilerplate on 50 of 50 events: "X takes place at VENUE in CITY on Friday 11 September. A, B, C and 34 more are on the lineup. The listed genre is techno." It repeats the title, venue, date, lineup and genre that are already separate fields. The render template then tells the model to print it under "What:". The `get_artist_events` instruction literally works around this ("do not repeat the lineup in both the event title and the description").
- `lineup` is uncapped. Festivals ship 40 to 51 names per event.
- `promoters` is an array of objects with slugs and ra.co URLs the model never uses.
- `image_url`, `lat`, `lng`, `source`, `pick` and `sound_tags` are on every event and used by nothing in the render template.

Fix:

- Detect the boilerplate template and drop `description` when it matches. When it does not match, keep the first 160 characters.
- Cap `lineup` at 8 names and add `lineup_count`.
- Flatten `promoters` to names.
- Drop `image_url`, `lat`, `lng`, `source`, `sound_tags` from list results. Keep them on `get_event`. Offer `fields: ["images", "coordinates"]` for callers such as the app that want them.
- Shorten the two redirect links to one base plus id, or emit one `links` object.
- Target: under 400 bytes per event in list results, which brings a 12-event search from 33 KB to roughly 10 KB on the wire and halves model tokens.

### F8. Result order is not chronological and sort controls are hidden

Default upstream ordering is by attendance. A Berlin weekend search returned Friday, Friday, Friday, Friday, Saturday, Saturday, Saturday, Sunday, Friday, Friday, Saturday, Saturday. The model renders that list with dates on each line, so the user sees a shuffled weekend.

Upstream supports `sort_by=soonest|popular|distance|cost|event_type` and `origin_lat`/`origin_lng`. `buildEventQuery` in `src/api.js:44-46` already forwards all of them, but none is in the tool schema, so the model can never ask for "soonest" or "closest to Kreuzberg".

Fix: expose `sort_by` with an enum and a description, default to `soonest` whenever the request is a single day, and expose `origin_lat`/`origin_lng` for "near me" requests (the privacy policy says coordinates are not requested, so document this as opt-in).

### F9. The ticket safety rails can be walked around

`quote_ticket_order` returns a locked quote as an unsigned base64 JSON `quote_token`. `purchase_ticket_order` decodes it and trusts every field.

Reproduced:

- A token edited to `max_total: 1`, `quantity: 1`, `purchase_mode: "partner_api_purchase"`, `checkout_url: "https://evil.example/pay"` was accepted. With no provider configured the response was `purchase_provider_not_configured`. The coverage audit went further and confirmed that with a provider configured, a token edited to quantity 12 and max_total 999999 reached `provider.purchase` unchanged, and the response was `purchased`.
- `validatePurchaseConfirmation` uses substring matching. "I am the buyer, 20 people, 120 dollars" satisfied a quote for 2 tickets at max 120, because "buy" is inside "buyer" and "2" is inside "20".

The hosted build only ever returns checkout handoff, so no money moves today. The rails are the product's stated safety story for Hermes and OpenClaw adapters, and they do not hold.

Fix: sign the token with HMAC-SHA256 using a server secret (`DIZKO_QUOTE_SIGNING_SECRET`, fall back to a per-process random key), verify before decoding, and refuse tokens whose `quote_id` does not recompute. Match confirmation with word boundaries and require the quantity and max total as whole numbers. Return a specific `confirmation_mismatch` error listing what was missing.

### F10. Data the DJ and venue audience wants is dropped

The upstream event object is 3.8 KB and rich. The MCP keeps 1.2 KB, and the wrong 1.2 KB.

| Upstream field | Present on Berlin events | MCP exposes it |
| --- | --- | --- |
| `billing` (set times per artist) | 48 of 50 | No |
| `venue_address` | 49 of 50 | No |
| `artist_socials` (SoundCloud, Instagram per lineup artist) | 44 of 50 | No |
| `title_en` and `description_en` | 19 of 50 | No |
| `search_fallback` (top-level, tells you the query fell back) | always | No |
| `unlocking` and `early` city lists | 20 cities | No |

Set times are the single most requested fact for "when does Ben Klock play". Venue address is what a directions link and a calendar entry should carry; today the calendar file says "AMT, berlin". `search_fallback` is how a messaging agent knows the search degraded.

Fix: add `set_times` (from `billing`, capped at 10), `address`, and `search_fallback` to summaries; add `artist_socials` to `get_event` and to the artist events response; prefer `title_en` when present and the user's language is English.

### F11. City handling hides coverage and rejects natural input

- `list_cities` returns only the 27 `live` cities. Upstream also serves 12 `unlocking` and 8 `early` cities, and `search_events` works for them: Bangkok returned events, Montreal has 76. The model tells users these cities are not covered.
- "Berlin, Germany" is rejected as unsupported. "NYC" and "LA" work because upstream normalizes them.
- The nearest-city fallback in `src/tools.js:851-863` is a hand-written map of ten UK cities and Potsdam. Hamburg, Munich, Lyon, Rotterdam and every other neighbor get no suggestion.
- `SUPPORTED_CITIES` in `src/config.js` is a static list of 47 that the CLI prints as "supported cities"; 20 of them are not live.

Fix: return all three buckets from `list_cities` with a `status` field; strip country suffixes from `city`; replace the UK map with a distance lookup over a small city coordinate table so the nearest live city is computed, not guessed.

### F12. Artist tools: duplicates, ordering, and a wasted round-trip

- `get_artist_events` for Ben Klock returned "2026-09-12 Anfiteatro De Pedra - Anfiteatro Professor Caldeira Cabral (lisbon)" and "2026-09-12 Anfiteatro de Pedra (lisbon)". Same show, two sources, listed twice.
- Events per artist are in popularity order, not date order. Nina Kraviz came back as 30 Oct, 13 Sep, 4 Oct, 9 Oct.
- The artist instruction tells the model to call `get_artist_page` to resolve a Dizko page link "and never guess it". Every handle tested (NinaKraviz, AvalonEmerson) returned `published: false`, so every artist question costs an extra call that returns nothing. Meanwhile `find_scene_entities` constructs `dizko_url` for every artist without checking, and `www.dizko.app/<anything>` returns 200 with the generic SPA page, so the link cannot be verified by the model either. Two tools give the model contradictory signals about the same URL.
- The DJ profile ships 30 `appearances`, most of them past, and 12 press clips from 2019 to 2022, in a 15 KB payload, with no upcoming or past split.
- `eventFeaturesArtist` accepts a description mention, so an event "inspired by Ben Klock" with a different lineup passes as his.

Fix: dedupe per artist on (date, normalized venue prefix); sort by `starts_at`; return `dizko_page_published` from the profile call and drop the separate page lookup from the instruction unless the user asks for a mix; split `appearances` into `upcoming` and `past_count`; require a lineup or title match, not a description match.

### F13. The roundup's top picks are not picks

Without a profile, every event that day gets +10 for "happens soon", so ties are broken by start time. Berlin's top five on the audit day were a Tuesday techno rave, a Ruby meetup, a walking tour titled "Hitler's Berlin", a boat cruise, and a bar night. `get_city_pulse` shows the same weakness: the "top venues" list is led by Minimal Bar with 7 events and 105 total attendance, above OXI with 6 events and 1,106 attendance, because venues sort by count first.

Fix: for unpersonalized roundups, rank by attendance, featured flag, and a time-of-day prior (parties after 21:00, talks before 20:00) instead of "happens soon". Sort top venues by attendance-weighted count.

## Priority 2: design, operations, hygiene

### F14. Tool names collide and the surface is wider than it needs to be

- No `dizko_` prefix. This session's own tool list contains `search_events` and `get_event` from a Google Calendar server. A user with both connected gets ambiguous routing.
- 24 tools. `search_events`, `recommend_events`, `recommend_events_for_user` and `plan_night` share one schema and differ only in ranking and whether a profile is attached. Four tools return static text with no data: `get_preference_onboarding`, `get_event_search_followups`, `get_ticket_purchase_policy`, and `get_event_feedback_prompt`. Each one costs the model a routing decision on every turn.
- Every tool's ChatGPT status label is "Working" / "Ready". The per-tool labels ("Searching live events", "Event recommendations ready") were removed in the registry-prep commit.

Proposed surface (18 tools, prefixed): `dizko_search_events` with optional `profile_id`/`profile_secret` and `rank: "relevance" | "taste"`, `dizko_plan_night`, `dizko_daily_roundup`, `dizko_city_pulse`, `dizko_get_event`, `dizko_list_cities`, `dizko_find_artist`, `dizko_find_venue`, `dizko_find_promoter`, `dizko_artist_events`, `dizko_create_profile`, `dizko_update_profile`, `dizko_get_profile`, `dizko_delete_profile`, `dizko_record_feedback`, `dizko_ticket_offers`, `dizko_quote_tickets`, `dizko_purchase_tickets`, `dizko_calendar_file`. Move the four static-text tools to MCP `prompts` or fold their text into descriptions and `instructions`.

### F15. Guidance contradicts itself

`MCP_SERVER_INSTRUCTIONS` says to answer a city-plus-timeframe request with a single search call and to call `get_event_search_followups` only when the assistant genuinely cannot infer what to ask. The followups tool's own `assistant_instruction` says to ask one or two questions first. `golden-prompts.md`, `USER_GUIDE.md`, the submission packet and the screenshot checklist all expect the followups call for "What's happening tonight in Berlin?". Pick one behavior and make the docs, the tool text, and the instructions agree. The single-call behavior is the right one for a chat product.

### F16. Rate limiting will throttle hosted clients at scale

The limiter is per-process, in memory, keyed by the first `X-Forwarded-For` hop, at 120 requests per minute. ChatGPT and Claude call from a small pool of shared egress addresses, so 120 per minute is the budget for every user of that client combined. Either raise the limit for known client ranges, key on a client-provided session hint when present, or move limiting to the edge.

### F17. The preference store cannot scale past one replica

`FilePreferenceStore` rewrites `preferences.json` on every write and on every read that prunes. Locking is a per-process promise queue, so two replicas would corrupt each other. Reads are O(profiles). This is fine for a pilot and a hard ceiling for a product. Plan a move to the API's own store or a small key-value database before scaling.

### F18. Calendar files have three bugs

- `DESCRIPTION` contains a literal backslash-n: the parts are joined with `"\\n"` and then `escapeIcs` doubles the backslash. Calendar apps show `\n` as text.
- No line folding at 75 octets (RFC 5545 section 3.1). Lines reach 93 characters.
- `LOCATION` is "AMT, berlin" although upstream has "Dircksenstraße 114 10178 Berlin". City slugs are lowercase everywhere in output because `venue_city` is a slug; map it to the display name from `/cities`.

### F19. Security posture worth stating explicitly

- CORS is `*` by default and the SDK handler performs no Origin or Host validation (by design in SDK 2.0, which expects the host to do it). With no bearer token, any web page can call every tool cross-origin. For a public read API that is defensible; profile writes are protected by the secret. State it in `SECURITY.md`.
- Short links under `/e/` bypass the bearer token when one is configured.
- A malformed percent-encoding in a short link id throws `URIError` and returns 500.
- `EVENTCHAT_ALLOW_LEGACY_PROFILE_IDS=true` disables secret checks for legacy profiles and is undocumented.

### F20. Docs, metadata, and verifiers are out of date

Details in Appendix A. The items that will bite first:

- `server.json` says version 0.7.3; the package is 0.7.6.
- The README lists 23 tools, `plugin-submission.md` lists 17, three documents say "21 tools", and `scripts/validate-submission-fields.mjs:143` requires the literal string "21 tool descriptors" while also requiring the evidence count to equal the real 24.
- `scripts/verify-submission.mjs:355` asserts the tool list is under 19,600 bytes. It is 19,890 bytes before the server adds its envelope, so `npm run verify:submission` and `preflight:submission` fail on this commit.
- `USER_GUIDE.md` and the screenshot checklist say "use this endpoint" and "do not use this custom domain yet" about the same URL.
- `get_ticket_purchase_policy` still advertises `uplayground_checkout` as a supported mode, and profile ids are prefixed `upg_`.
- The `build:mcpb` manifest says "32 live cities". There are 27.

### F21. Test gaps that matter

Details in Appendix B. The three that should be closed first: the ticket module is at 58% branch coverage with the tampering, expiry, and provider-success paths untested; no test exercises `resolveDateRange` at any time other than noon UTC; and the consent and confirm gates for `create`, `save` and `delete` are only tested through the missing-argument path, so a `consent: false` with all fields present has never been asserted.

## Notes for the app and the messaging agent

- Nothing in the payload tells a consumer the time zone. Until F1 ships, every consumer must convert using its own city table, and any consumer that does not is showing wrong times. This is the first thing to fix.
- The daily roundup is 9,600 tokens for one city. A push-style messaging agent needs a `compact: true` mode that returns title, when, venue, price and url only, and caps sections at three.
- `search_fallback` from upstream is dropped. A messaging agent cannot tell whether "no results" means nothing is on or the query degraded.
- There is no event `status` or `updated_at` in the upstream payload as served, so a messaging agent cannot detect cancellations or lineup changes. That is an API gap to raise with the backend team; the MCP can only pass through what exists.
- Artist tracking through a saved `featuring` list works and is the right hook for "tell me when X plays near me" notifications, once F12's dedupe and ordering are fixed.
- The `count` field on search is the total available, not the page size. Consumers paging with `offset` should use it; the README says so but the served schema does not.

## Recommended roadmap

Sprint 1, correctness (F1, F2, F3, F4, F6): local times and city-timezone date resolution; taste as ranking hints only; feedback learning guards; token-based venue matching; the shared error shape with pre-network validation. These are the changes that stop wrong answers.

Sprint 2, labeling and cost (F5, F7, F8, F10): restore descriptions and defaults and rewrite tool descriptions; slim the event summary; expose `sort_by` and default single-day searches to soonest; add set times, address and `search_fallback`.

Sprint 3, design and safety (F9, F11, F12, F13, F14, F15): sign quote tokens and fix confirmation matching; three-bucket cities with computed nearest; artist dedupe and ordering; roundup ranking; prefix and consolidate tools; reconcile guidance.

Sprint 4, hygiene (F16 to F21): edge rate limiting; store migration plan; calendar fixes; security posture doc; docs and verifier reconciliation; the tests in Appendix B.

## Appendix C: MCP SDK 2.0 conformance

- The low-level `Server` with string method names is a supported v2 API (marked deprecated in favor of `McpServer`). Request validation on this path checks only that `name` is a string and `arguments` is an object. `inputSchema` and `outputSchema` are never consulted. `McpServer.registerTool` is the path that validates.
- `instructions` is emitted on both the legacy `initialize` and the modern `server/discover`. `cacheHints` is real and correctly stamped on modern responses only.
- Non-standard tool fields (`securitySchemes`, `_meta`, partial `annotations`) pass through verbatim on both eras. No annotation is required by the schema.
- `{ content, structuredContent, isError }` is accepted; `structuredContent` must be an object on the 2025 era, which `toolJson` guarantees. Error results are not held to `outputSchema` by the SDK.
- `toNodeHandler(request, response, parsedBody)` honors the pre-parsed body and never re-reads the consumed stream.
- The modern path requires `Mcp-Method` on every request and `Mcp-Name` on `tools/call`; it does not require `Accept`. The legacy path is stateless, needs no `initialize`, requires both `Accept` types, and supports batches. Modern batches are rejected by the SDK.
- `createMcpHandler` performs no Origin or Host validation; `httpServer.js` adds none, and CORS never rejects. `Origin: https://evil.example` was served with `Access-Control-Allow-Origin: *`.
- The in-process `handleMcpRequest` helper drifts from the SDK: it echoed any client `protocolVersion` on `initialize` where the SDK negotiates to a supported version (fixed: it now negotiates against the SDK's own `SUPPORTED_PROTOCOL_VERSIONS`); it stamps `resultType` and cache fields on legacy-era responses where the SDK never does; it answers `server/discover` on the legacy path where the SDK returns method-not-found; and it hard-codes version constants the SDK exports.
- With the SDK doing no input validation, `search_events` with `arguments: {}` ran a global search across all cities (35,531 events at audit time). Fixed: `dizko_search_events` now requires a scope (city, query, venue, featuring, promoter or neighborhoods) and `src/validate.js` checks every argument before any network call.

Tracing the upstream calls shows the MCP contributes roughly 30 to 50 ms of
that, and every tool above makes exactly one upstream request except
`dizko_artist_events`, which fans out one per artist in parallel. The rest
is `api.dizko.app`.

That upstream time is bimodal and does not depend on what is asked for. The
same URL requested ten times in a row over a warm connection returned in
566, 2101, 276, 249, 3488, 919, 381, 3548, 2771 and 353 ms. Response size
is not the driver: `limit=10` and `limit=200` have indistinguishable
distributions. Concurrency does not help and may hurt: six identical
requests in parallel took 5465 ms in total, worse than the sequential
median, and an eight-artist fan-out at concurrency 8, 4, 3, 2 and 1 gave
results whose ordering reversed between two trials, so the variance swamps
any pooling signal.

Two conclusions:

- There is no client-side fix worth making here. Connection pooling is
  already in effect, hedged requests would add load to an upstream that
  degrades under parallelism, and a concurrency limit cannot be justified on
  data this noisy. The response cache already turns every repeat inside the
  TTL into a 1 to 14 ms answer.
- The tail belongs to the API. A p50 near 900 ms with a p90 above 3 s is the
  single largest contributor to how slow an assistant feels on a first
  question, and it is worth investigating on the API side: whether the spikes
  are cold containers, connection-pool exhaustion to the database, or a
  query that is not using an index.
