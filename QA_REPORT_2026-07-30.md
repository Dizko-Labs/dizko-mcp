# Dizko Events MCP QA Report

Date: 2026-07-30

## Scope

This pass tested the live Dizko MCP as a new user and then updated the MCP package in this repo to fix the highest-value issues found in search, personalization, client compatibility, docs, and growth surfaces.

## Live findings

### What worked well

- Public search returned live, relevant events.
- Preference creation was consent-first and returned a one-time `profile_secret`.
- Feedback recording worked and extracted learned signals from natural-language notes.
- Event payloads consistently linked back to Dizko event pages, ticket sources, calendar links, and directions.
- Event pages on `www.dizko.app` include a visible path to the iPhone app via `/ios` and App Store CTAs.

### Problems found

#### 1. Personalized recommendation narrowing was too aggressive

Observed behavior:
- After positive feedback on an event at ÆDEN, the next personalized recommendation round collapsed to a single venue.
- The likely cause was venue affinity being treated like a hard search filter instead of a ranking hint.

Impact:
- Users see artificially narrow results.
- Learned taste behaves like a brittle filter, not a helpful ranking layer.

Recommended product behavior:
- Saved and learned taste should widen candidate recall, then rank.
- Only explicit user constraints should become hard filters.

#### 2. MCP tool metadata was not compatible with some clients

Observed behavior:
- `mcporter` rejected the live tool metadata because top-level `outputSchema` used `anyOf` without a top-level `type: "object"`.

Impact:
- Some MCP clients can talk to the server over raw JSON-RPC, but fail discovery or schema validation.

Recommended product behavior:
- Keep the success and error branches, but expose a client-friendly top-level object schema.

#### 3. Public defaults and docs were stale in the repo package

Observed behavior:
- The package still referenced old Railway and old brand URLs in config defaults, docs, support pages, security.txt content, and submission scripts.

Impact:
- Local installs and verification scripts can point at the wrong surfaces.
- Public setup docs can confuse users and reviewers.

#### 4. Marketing handoff to the Dizko app was implicit, not explicit, in MCP responses

Observed behavior:
- Event payloads already linked to Dizko event pages.
- Those pages do include App Store paths.
- But the MCP response itself did not expose a clean app-download URL for assistants to mention.

Impact:
- Assistants can send people to the event page, but they are not given a direct product-growth hook in structured output.

## Changes implemented in this repo

### 1. Fixed personalization narrowing logic

Changed `recommend_events_for_user` so learned preferences do not silently become hard search filters.

New behavior:
- Saved city can still seed the search when the user omits a city.
- Explicit current-request fields stay as hard filters.
- Saved and learned taste now mainly informs ranking.
- Learned venue affinity no longer becomes an automatic `venue=` API filter.

Added a regression test for this.

### 2. Improved MCP schema compatibility

Updated the shared `withError()` schema wrapper so top-level `outputSchema` now includes `type: "object"` while still keeping success and error branches.

Expected effect:
- Better compatibility with clients that require top-level object output schemas during tool discovery.

### 3. Updated current production defaults

Updated package defaults to live Dizko surfaces:
- API: `https://api.dizko.app`
- Web: `https://www.dizko.app`
- MCP: `https://mcp.dizko.app/mcp`
- App download: `https://www.dizko.app/ios`

### 4. Added structured app-download surfacing

Added `app_download_url` to user-facing event result outputs so assistants can explicitly mention the Dizko iPhone app when relevant.

Applied to:
- `search_events`
- `recommend_events`
- `recommend_events_for_user`
- `plan_night`
- `get_event`

Also updated assistant instructions to mention the app only when it is relevant to the user.

### 5. Updated support, security, and deployment docs

Updated package docs and public pages to current Dizko domains and emails, including:
- support pages
- privacy page
- terms page
- user guide
- install page
- deployment docs
- submission packet and audit
- verification scripts
- security contacts

### 6. Updated calendar identity

Updated generated calendar UID branding from the old domain to Dizko.

## Remaining suggested improvements

These were not implemented in this pass, but they are still worth doing.

### A. Make no-result responses more helpful

Current behavior can return `count: 0` with no relaxation advice.

Suggested improvement:
- Add structured `suggested_relaxations`, such as:
  - remove vibe filter
  - increase price cap
  - broaden timeframe
  - expand to nearby neighborhoods

### B. Add local-time rendering hints

Current event timestamps are ISO strings. That is correct for machines, but assistants often need help rendering user-friendly local times.

Suggested improvement:
- Add `timezone` or `starts_at_local` fields where reliable.
- Or add a rendering hint that the assistant should convert to the event city timezone.

### C. Increase confidence around crowd feedback

The live run showed that crowd dislike can still be under-weighted in ranking if recall is too narrow or if popularity signals dominate.

Suggested improvement:
- Add stronger penalties when learned avoid terms include crowd-related signals.
- Consider crowd-aware caps when attendance is very high and the user has learned avoid terms like `crowded` or `huge crowds`.

### D. Add product-growth guidance without spam

Now that `app_download_url` exists, the next step is policy.

Suggested assistant behavior:
- Mention the app only when a user shows repeat intent, wants saved preferences, wants mobile usage, or asks for planning/saving/sharing.
- Do not append app promo to every result list.

### E. Add a live cross-client compatibility check

Suggested improvement:
- Add one verifier that confirms tool discovery works in at least:
  - raw HTTP JSON-RPC
  - local stdio
  - a strict schema client

## Summary

The main code fix was to stop learned venue preference from collapsing personalized search recall. The main compatibility fix was adding a top-level object type to output schemas. The main growth fix was exposing a structured app-download URL while keeping event pages on Dizko. The main maintenance fix was moving the package defaults, docs, and verification scripts onto the real Dizko production domains.
